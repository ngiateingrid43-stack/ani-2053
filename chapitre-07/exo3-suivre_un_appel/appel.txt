Les sauts :
1. NkCanvasApp.h — OnRender(NkRenderWindow &target) : la méthode virtuelle que l'application redéfinit. Elle reçoit une référence à la cible CONCRÈTE (NkRenderWindow), pas à NkRenderTarget. C'est ici que l'utilisateur écrit target.Clear(couleur). Ce qui s'y décide : le type statique de `target` est NkRenderWindow, donc la résolution de Clear part de cette classe concrète — pas de la classe abstraite.
2. NkRenderWindow.h — class NkRenderWindow : public NkRenderTarget, ligne `void Clear(const NkColor2D &color = NkColor2D::Black) override;`. Ce qui s'y décide : NkRenderWindow redéclare Clear en override, donc c'est bien cette classe qui fournit l'implémentation concrète pour l'écran. Le corps, lui, n'est PAS dans l'en-tête : il est dans NkRenderWindow.cpp, absent du kit (le kit ne contient que include/ et lib/).
3. NkRenderTarget.h — class NkRenderTarget, ligne `virtual void Clear(const NkColor2D &color = NkColor2D::Black) = 0;`. Ce qui s'y décide : le contrat abstrait. Toute cible de rendu (écran ou texture offscreen) doit vider son framebuffer avec une couleur. Le `= 0` en fait une virtuelle pure : aucune implémentation ici, donc aucun saut de plus possible par cette branche de l'héritage — il faut redescendre vers la classe concrète.

Arrêt :
NkRenderWindow::Clear — la surcharge concrète déclarée en override dans NkRenderWindow.h. Son corps n'est pas dans le kit : il est compilé dans lib/Debug-Windows/NKCanvas.lib (et lib/Release-Windows/NKCanvas.lib).

Pourquoi là :
Deux signaux, l'un après l'autre. D'abord la virtuelle pure `virtual void Clear(...) = 0` dans NkRenderTarget.h : c'est un fond au sens de l'énoncé — à ce point, la route devient un embranchement (NkRenderWindow pour l'écran, NkRenderTexture pour l'offscreen), et la suite dépend de la classe concrète. Ensuite, à l'embranchement choisi (NkRenderWindow), la déclaration `override` de NkRenderWindow.h n'a pas de corps dans l'en-tête, et le kit ne fournit aucun .cpp : le corps est dans la bibliothèque compilée lib/NKCanvas.lib. Une méthode déclarée override dans un en-tête n'a pas forcément son corps à côté — c'est le piège de l'exercice, et c'est exactement ce qui se passe ici. On s'arrête sur une bibliothèque déjà compilée, troisième type de fond admis par l'énoncé.

Ce que je sais maintenant :
Ce que je sais, et que j'ai VU dans les en-têtes : (1) l'appel `target.Clear(couleur)` dans `OnRender` part d'une référence à NkRenderWindow, pas à NkRenderTarget — le type concret est connu dès la signature ; (2) NkRenderWindow redéclare Clear en override, donc c'est bien cette classe qui porte l'implémentation pour l'écran ; (3) NkRenderTarget déclare Clear en virtuelle pure (= 0), donc le contrat est « vider le framebuffer avec une couleur » et il existe au moins une autre implémentation concrète (NkRenderTexture, citée dans le commentaire d'en-tête de NkRenderTarget.h) ; (4) le kit ne contient aucun .cpp, seulement include/ et lib/ — donc le corps de NkRenderWindow::Clear est nécessairement dans la bibliothèque compilée, et on ne peut pas le lire.

Ce que je SUPPOSE, sans l'avoir vu : (a) le corps de NkRenderWindow::Clear appelle très probablement GetRenderer()->Clear(color) ou une méthode équivalente du NkIRenderer2D sous-jacent — c'est la seule façon plausible de déléguer à un backend OpenGL/Vulkan/DX11/DX12/Software sans dupliquer le code dans NkRenderWindow, et NkRenderTarget.h expose justement GetRenderer() pour cela ; (b) NkIRenderer2D::Clear est très probablement une autre virtuelle pure (= 0), ce qui ferait un saut de plus vers une implémentation par backend — mais je ne l'ai pas vérifié, donc je ne l'affirme pas ; (c) le backend effectue un `glClear` (OpenGL), un `vkCmdClearAttachments` (Vulkan), un `ClearRenderTargetView` (DX11/12) ou un memset (Software) — mais c'est une supposition sur le corps, pas une lecture. Ce que j'affirme, c'est uniquement le chemin dans les en-têtes : OnRender → NkRenderWindow::Clear (déclarée) → NkRenderTarget::Clear (= 0, fond) → NkRenderWindow::Clear (corps dans la bibliothèque, fond).
