Le long :
include/NKContainers/Sequential/NkVector.h
2566 lignes (comptées avec Get-ChildItem + Measure-Object -Line, hors include/Embedded/ et glad/).

Le difficile :
include/NKWindow/Core/NkWindowConfig.h
225 lignes (comptées avec Get-ChildItem + Measure-Object -Line, hors include/Embedded/ et glad/).

Ce qu'ils gardent :
NkVector.h garde exactement quatre choses, et rien d'autre : un pointeur T *mData (le buffer), un SizeType mSize (le nombre d'éléments), un SizeType mCapacity (la capacité allouée), et un Allocator *mAllocator (le pointeur vers l'allocateur). Ces quatre champs sont modifiés ensemble, dans cinq méthodes privées seulement : Reallocate(), ReallocateAndEmplace(), MoveOrCopyRange(), DestroyRange(), ConstructAt(). Toutes les méthodes publiques (PushBack, PopBack, Insert, Erase, Resize, Clear, Reserve, ShrinkToFit, Swap, les six constructeurs, les quatre opérateurs d'affectation) passent par ces cinq méthodes. Le reste du fichier — plus de 2000 des 2566 lignes — est de la documentation Doxygen (@brief, @note, @example) et des commentaires historiques.

NkWindowConfig.h garde environ soixante-dix champs si l'on compte les sous-structures. À plat : huit champs de position et taille (x, y, width, height, minWidth, minHeight, maxWidth, maxHeight), treize champs de comportement (centered, resizable, movable, closable, minimizable, maximizable, canFullscreen, fullscreen, modal, vsync, dropEnabled, screenOrientation, respectSafeArea), six champs d'apparence (frame, hasShadow, transparent, visible, bgColor, noActivate), trois champs de fenêtre discrète (alwaysOnTop, clickThrough, opacity), quatre champs d'identité (title, name, iconPath, iconImages), deux champs mobile (hideSystemUI, lockOrientation), et deux sous-structs (webInput avec neuf champs, native avec cinq champs, surfaceHints). Ces champs changent depuis au moins cinq endroits distincts : (1) l'application les remplit, souvent via NkCanvasAppConfig::fenetre qui n'en recopiait que six sur vingt-cinq avant le 25/09/2026 ; (2) NkWindow::Create() les lit champ par champ, avec des règles de priorité différentes par dorsal ; (3) NkGraphicsContextFactory::PrepareWindowConfig() les modifie pour OpenGL/GLX uniquement ; (4) NkWindowAudit.h les audite et écrit un « refus nommé » au journal quand le dorsal ne tient pas un réglage ; (5) l'application les restaure au démarrage (le bug des +16 px de largeur et +39 px de hauteur à chaque lancement, documenté dans le contrat taille/position).

L'écart :
Le critère qui explique l'écart n'est pas la longueur — c'est le nombre de choses gardées, et le nombre d'endroits d'où on peut les changer.

NkVector.h est long (2566 lignes) mais il ne garde que quatre choses, et il les garde bien : un seul invariant (mData/mSize/mCapacity cohérents), un seul point de passage obligé (les cinq méthodes privées de Reallocate/ReallocateAndEmplace/DestroyRange/MoveOrCopyRange/ConstructAt), et toutes les méthodes publiques y convergent. C'est le cas d'école de l'énoncé : « deux mille lignes qui ne gardent rien se lisent en une heure ». La lecture est même facilitée par un récit linéaire — les commentaires racontent l'historique (le bug du 08/10 sur v.PushBack(v[0]), les versions v1.1.0, les notes de migration STL) — mais ce récit n'est pas le code : le code lui-même est une seule classe avec quatre champs et une vingtaine de méthodes, dont la moitié sont des alias (begin/end pour range-based for, size/capacity pour compat STL, Empty/IsEmpty/empty pour les trois conventions de nommage). Une fois qu'on a compris ReallocateAndEmplace, on a compris tout le fichier.

NkWindowConfig.h est court (225 lignes) mais il garde environ soixante-dix champs, et ces champs changent depuis cinq endroits distincts, avec des règles différentes par dorsal : l'application les remplit, NkWindow::Create les lit, NkGraphicsContextFactory les prépare (pour OpenGL/GLX seulement), NkWindowAudit les audite, et l'application les restaure. Le commentaire d'en-tête le dit explicitement : « TOUS CES REGLAGES NE SONT PAS TENUS PAR TOUS LES DORSAUX » — la doc est donc la seule source de vérité sur ce que fait chaque champ sur chaque plateforme, et cette doc est dans le commentaire, pas dans le code. C'est le cas d'école inverse : « trois cents lignes avec sept variables globales modifiées depuis cinq endroits vous occuperont la journée ». Ici, c'est 225 lignes avec 70 champs modifiés depuis 5 endroits, et un audit qui refuse à voix haute ce qu'il ne peut pas tenir. Le fichier résiste, non parce que son domaine est difficile (une config de fenêtre, c'est trivial), mais parce qu'il faut tenir en tête 70 champs × 5 endroits × N dorsaux pour prédire ce que fera la fenêtre à l'exécution.

En résumé : NkVector.h est long et facile parce qu'il garde peu et concentre les mutations. NkWindowConfig.h est court et difficile parce qu'il garde beaucoup et disperse les mutations. La longueur ne prédit rien ; le nombre de choses gardées et le nombre d'endroits où on les change prédit tout.
