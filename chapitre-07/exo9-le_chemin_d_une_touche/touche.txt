Les couches :
1. NKWindow/Platform/Win32/NkWin32EventSystem.h (dans lib/NKWindow, absent du kit) — Windows envoie WM_KEYDOWN à la fenêtre. Le message est capté par WindowProcStatic (déclaré dans NkEventSystem.h, ligne « static LRESULT CALLBACK WindowProcStatic(HWND, UINT, WPARAM, LPARAM) »). Le lien entre le système Windows et NkEventSystem vient du code (WindowProcStatic est la callback que Win32 appelle, NkEventSystem.h le déclare en public dans la section Platform-specific). Ce qui s'y décide : le message brut (HWND, UINT msg=WM_KEYDOWN, WPARAM vk, LPARAM lparam) entre dans le moteur.

2. NKEvent/NkEventSystem.h — NkEventSystem::ProcessMessage(HWND, UINT, WPARAM, LPARAM, NkWindowId, NkWindow*) et NkEventSystem::VkeyToNkKey(UINT vk, bool extended) noexcept. Le lien vient du code : ProcessMessage est déclaré private dans la section « Platform-specific methods » de NkEventSystem, et VkeyToNkKey est le convertisseur VK_* → NkKey. Ce qui s'y décide : le VK_* Windows est traduit en NkKey (touche logique, position US-QWERTY), et le message est routé vers NkEventSystem::Enqueue(evt, winId) (déclaré private, « Point 4 : Enqueue prend le winId explicitement pour que chaque event sache exactement à quelle fenêtre il appartient »).

3. NKEvent/NkKeyboardEvent.h — NkKeyPressEvent(NkKey key, NkScancode scancode, NkModifierState mods, uint32 nativeKey, bool extended, uint64 windowId). Le lien vient du code : NkEventSystem::ProcessMessage construit l'événement NkKeyPressEvent à partir du VK_* et du scancode, en appelant VkeyToNkKey et NkScancodeFromWin32 (déclarée dans NkKeyboardEvent.h, « NkScancode NkScancodeFromWin32(uint32 win32Scancode, bool extended) noexcept »). Ce qui s'y décide : le type d'événement (NK_KEY_PRESSED), la touche logique (NkKey), le scancode physique (NkScancode), les modificateurs (NkModifierState), le code natif (uint32 nativeKey), et l'identifiant de fenêtre (windowId).

4. NKEvent/NkEventSystem.h — NkEventSystem::DispatchToCallbacks(NkEvent *ev, NkWindowId winId). Le lien vient du code : la méthode est déclarée private dans NkEventSystem, et elle est appelée depuis PumpOS() pour router l'événement vers les callbacks enregistrés. Ce qui s'y décide : la distribution de l'événement vers les callbacks typés (mTypedCallbacks), globaux (mGlobalCallback), et par fenêtre (mWindowCallbacks). C'est ici que le filtrage par type et par windowId se fait.

5. NKEvent/NkEventDispatcher.h — NkEventDispatcher(NkEvent *ev) puis NK_DISPATCH(dispatcher, NkKeyPressEvent, OnKeyPress) dans le OnEvent de l'application. Le lien vient du code : la macro NK_DISPATCH (ligne ~180 de NkEventDispatcher.h) appelle dispatcher.Dispatch<NkKeyPressEvent>(lambda). Ce qui s'y décide : le dispatch typé — le handler est appelé avec NkKeyPressEvent&, et si le handler retourne true, l'événement est marqué traité (MarkHandled()) et la propagation s'arrête.

6. NKCanvas/App/NkCanvasApp.h — OnEvent(const NkEvent&) et OnKeyPress(const NkKeyPressEvent&) de NkCanvasApp. Le lien vient du code (NkCanvasApp.h, section « LES ÉVÉNEMENTS — trois entrees, UN SEUL CHEMIN ») : « niveau 1 OnEvent(const NkEvent&) -> bool. Le brut. true = consomme. niveau 2 OnPointer / OnKey / OnResize. DERIVES du niveau 1, jamais d'un second abonnement ». Ce qui s'y décide : la coquille NkCanvasApp dérive OnKeyPress depuis OnEvent, et appelle la méthode virtuelle de l'application. C'est ici que l'application reçoit l'événement.

Où je me suis arrêté :
Je me suis arrêté au premier saut, parce que le corps de WindowProcStatic (dans NkWin32EventSystem.cpp) et le corps de ProcessMessage (dans NkEventSystem.cpp) ne sont PAS livrés dans le kit : le kit ne contient que include/ (en-têtes) et lib/ (bibliothèques compilées), comme le dit KIT.txt. Les fichiers .cpp de NKWindow et NKEvent ne sont pas dans le kit. J'ai donc vu la chaîne de déclarations dans les en-têtes, mais pas les corps : la traduction effective de WM_KEYDOWN en NkKeyPressEvent (quel VK_* donne quel NkKey) n'est pas visible, elle est compilée dans lib/Debug-Windows/NKWindow.lib et lib/Debug-Windows/NKEvent.lib. De même, la façon exacte dont DispatchToCallbacks itère sur les callbacks n'est pas visible (mais la structure est claire : mTypedCallbacks, mGlobalCallback, mWindowCallbacks).
